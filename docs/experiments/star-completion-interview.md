10. 与原 STAR 的一致性按核心机制和可观察行为逐项判断；Intern S2/API、Workbench 控制和更严格隔离环境作为明确适配项，论文与源码冲突单列说明。用户已确认此标准。
11. 用户允许模型自行编写并运行受控的数学计算 Python。执行环境须限制文件访问、网络、运行时间与资源消耗，实际代码和输出形成可核验记录；计算结果只支持被检查的范围，不自动证明整题正确。

## 功能有效性的强制验收原则

- 每项核心机制建立“触发条件 → 决策 → 实际动作 → 持久状态 → 用户可见结果”的证据链，关联同一 Run、动作和状态版本。
- 验收从 Workbench 使用的公开 Job/Run 接口进入，覆盖实际 STAR 调度、S3 控制/账本和 S4 最终对象绑定。只测私有 helper 或另起测试专用执行路径不能验收产品集成。
- 设计能区分正确执行与绕过的反例：预算不足时确实没有外部派发；取消后没有新动作；答案改写后旧证据确实失效；重启后已完成动作不重跑。
- 对关键机制做有针对性的敏感性检查：故意绕过预算、取消栅栏、审查或答案绑定时，对应验收必须失败。检查不能仅断言代码自己生成的成功标志。
- 简单问题可以依法走 Explore 快通道。没有触发某机制时记录适用性及跳过原因，不为展示所有模块而强制增加调用。
- 明确区分 scripted、故障注入和真实 provider 证据。测试通过不推导真实模型行为；单次模型审查通过不推导数学正确率提升。

## 拟定实施顺序与退出条件

1. 原始来源逐项审计、现有功能有效性审计、控制恢复与隔离执行风险验证。退出条件是差距和有意适配可审阅，关键风险有可执行证据。
2. Workbench → Job → STAR 求解器 → 原账本/控制 → 最终 Evidence 的最小完整纵切；加入严格参考模式配置。退出条件是公共接口确实走此路径，非法配置不能启动。
3. 全部核心机制贯通、安全阶段恢复、取消/迟到结果与最终对象绑定。退出条件是关键分支和旁路反例均通过公共接口验收，已完成动作不重复执行。
4. 受控 Python 执行、真实代码/输出产物引用、适用验证范围；独立 Best-Effort 扩展。退出条件是执行限制实际生效，引用可解析且内容可核验，受限能力不冒充完整参考模式。
5. 原论文/固定源码二次比对、独立双轴审查、真实 Intern 验收、前端故障场景、全量发布检查。退出条件是核心合同无缺失、真实与注入证据分开、已知差异及成本完整记录。
