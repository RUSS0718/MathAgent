本轮按用户要求优先复用历史真实实验，新增provider/模型/工具派发均为0，未修改产品代码或运行全量测试。范围为readiness14至28的15份本地登记；这是事后比较，不是预登记、随机化或同时段配对实验，不是#128的线上pair。

## 样本与完整分母

目标octagon-colorings原始文本SHA256为395f5e9269c997fcc111fcd86b4a35bda59f6f63e15160bb41d63fbfc6f0be94。15至28登记为相同文本；原14登记哈希错误，出网前失败，另列。对有实际自然题Job的记录核对数据库problem与原题文本（仅忽略首尾空白）一致。

## 哪些可以放在一起比较

所有实际完成失败批次都核对manifest哈希、服务脚本哈希与execution policy一致、注册manifest副本一致；有终态预算的Job限额均与manifest一致。模型intern-s2/thinking=false/temperature0.2/output32768、Run14400秒、模型/HTTP128、工具32、预留16777216与stream_first保持；产品源码变化是观察因素，运行环境/模型服务状态未被实验控制。

只去除端口差异后，对服务脚本和其余登记控制项分组：

- A：15—20，单调用900秒，底层connect/read=(10,30)。可描述同登记环境下多个源码结果，但每版本样本极少，轨迹、时间段不同。
- B：21、24、25，单调用1200秒，底层connect/read=(10,30)。22/23也属于该配置组，但取消/未运行不并入模型交付率。
- C：26—28，单调用1200秒，底层connect/read由冻结stream_idle_seconds=30生成，即(30,30)。这三次同时具有相同产品source SHA与相同服务脚本，最适合观察固定版本内部的运行差异。

25与26虽产品SHA相同，但底层连接限制改变，不能只看manifest1200就认定实际传输完全相同。20与21产品SHA相同，但调用截止900→1200，不能算单独源码效果。跨A/B/C比较必须保留这些混杂因素。

## 能支持与不能支持的结论

1. 所查历史里没有一个这道题的已通过完整闭环版本可作为“可靠旧baseline”。主指标完整交付始终0，不能据此证明新版提升；也没有观察到“旧版交付成功、新版退化为失败”的证据。
2. 部分旧运行确实接受更多步骤：15为5，21为4，新27/28为0。这是描述性差异，不能淡化。但计划步数从4到16不等、步骤含义不同，阶段深度不是统一结果指标，不能由此推出退化的因果关系。
3. 固定版本也存在明显差异：18/19相同产品与控制项，接受0/1步，调用4/12；26/27/28相同产品和封装，接受3/0/0步、调用22/19/13、失败前64.27/30.21/17.21分钟。后者证明最近三次差异不需要源码变化即可出现；不能进一步把全部差异唯一归因于随机性，因为provider时段、环境与生成计划未固定。
4. 失败类型并未随版本单调变化：有JSON、合法审查异议、模型工具代码错误、计算证据不适用、网络中断与观察器失败。修复其中一类不保证另外一类不会阻断整题，不能把每次failed等同于“同一个bug没修好”。
5. 历史资料支持“当前仍无法稳定完成该题，且尚未证明版本改进提升整题交付”，不支持“每改一次都更差”，也不支持“所有改动没有副作用”。小样本和交付指标全失败的地板效应使版本排序不充分。

## 下一步如何获得因果证据

本次按用户要求复用历史，没有为了制造对照而继续付费。若必须判断回退哪项改动，需要额外前瞻试验：选择明确旧源码与当前源码，统一服务传输封装/模型/预算/同题输入，按预登记顺序交错串行运行，每臂固定重复次数，保留全部失败/未知。主指标仍完整交付，次指标为统一定义的格式失败、工具执行失败与证据适用性，不用不同计划的接受步数替代交付。不能把这种后续比较冒充已完成的#128，后者仍受#127前置约束；也不能通过降低审查门槛或best-effort宣称回归通过。
