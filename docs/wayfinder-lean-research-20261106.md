# Wayfinder：Lean 验证与形式化缓存的可信边界

研究日期：2026-11-06（Asia/Shanghai）。对应 Issue [#133](https://github.com/RUSS0718/MathAgent/issues/133)，供父任务 #130 引用。本文是研究结论和待验收建议，不是产品实现或能力报告。

## 结论

**可以在现有 Showcase 隔离工具架构上设计真实检查闭环，但当前仓库尚未具备该能力。** 固定目标、可信依赖、证明核验、公理政策、规格对应和证据绑定需要一起验收。容器退出码为零、类名存在、模型 ACCEPT 或源码没有 `sorry` 字符串，都不足以给出 L2/L3 结论。[S1–S3、R1–R3]

已有证明的检查与自动生成证明必须分开：前者核对提交的证明是否在指定环境和公理下证明指定命题；后者还需要翻译、搜索与修复，Lean 的检查能力不提供模型生成成功率保证。关键引理通过只能标 L2；L3 还要求原题全部义务与完整形式目标对应，不能由几个局部结果外推。[S1、R4]

首版建议只接受可信模板中的有理数多项式恒等式，先检查预先审阅的证明，再单独评价自动生成；目标缓存放在闭环之后，命中必须重验。对任意未审阅 AI 生成 Lean 程序，仅“模板 + 编译 + 公理名单”不宜称作最强验证；官方另列了可信 challenge、隔离构建、comparator 与外部检查器的增强路径。[S1]

## 1. 已确认事实

### 1.1 当前仓库

- 基准提交为 `b7038798cccdf5bfdc80175ebfe68dcbf12dc2d6`。`showcase/star_result_semantics.py::result_semantics` 返回的 `formal_verification` 固定为 `not_verified`；公开合同也明确 LLM 审查、有限计算不是形式证明。[R1]
- 本轮用 `rg --files` 核对指定 worktree，未发现 `lean-toolchain`、`lakefile.*`、`lake-manifest.json` 或 `.lean` 文件。这个结论限于仓库文件，不推断机器或外部服务是否安装 Lean。既有调研也记录未找到 Lean 执行器，checkpoint/回放不是证明缓存。[R3]
- SP-09 已规定固定镜像 ID、禁网、只读根目录、非 root、资源和输出限制、清理核实、Run 归属与内容哈希证据。它是 Python 工具的已接受合同，不表示 Lean 镜像、预算、检查器或导出链已经验收。[R2]

### 1.2 证明、公理与规格

Lean kernel 接受的是环境中具体形式命题的证明，前提包括导入定义、定理与公理。官方明确区分“有有效证明”和“定理陈述的含义”；记号、类型类与定义也可能影响后者。原题到形式目标的忠实性没有因 kernel 接受而自动获得保证。[S1]

`#print axioms` 报告目标直接和间接使用的公理。官方标准公理为 `propext`、`Classical.choice`、`Quot.sound`；`sorryAx` 表示目标或依赖不完整，其他自定义公理须另外判断。固定源码的 `collectAxioms` 遍历声明类型与值，并为导入声明使用预计算依赖；因此审计只检查当前文件文本会漏掉传递依赖。[S1、S2]

固定 Lean 源码中，`Lake.Check.checkAxioms` 接受目标和合法公理集合，检查引用闭包；它还区分 theorem 与 definition 目标。这证明有官方实现入口，不证明当前项目已调用它，也不意味着该内部 API 在其他版本稳定。[S3]

公理审计不能发现形式目标中额外添加的局部假设，例如把待证命题本身作为前提；这类条件属于目标类型和规格审核。一个条件定理在逻辑上成立，不等于无条件原题已解。[S1；此项为基于目标含义的推论]

官方验证文档给出的增强层次包括：普通检查、公理审计、`lean4checker --fresh` 重放 `.olean` 中证明，以及可信 challenge 配合 comparator/外部检查器。`lean4checker` 仍信任 `.olean` 结构，不负责证明自然语言规格对应；增强检查也保留逻辑、检查器、隔离环境和人工规格错误等信任前提。[S1]

原生求值涉及版本相关的额外信任：官方说明 4.29.0 起相关计算引入各自公理，`Lean.trustCompiler` 机制于 4.35.0 移除。因此不能只匹配旧名字来阻止原生计算；首版采用精确允许名单，任何名单外依赖均不提升验证等级。[S1；最后一句为建议]

### 1.3 版本与构建缓存

本次抓取的 Mathlib 固定提交 `9c8f67d65b5d8c67f658e4666accdfa45fa57a76` 中，`lean-toolchain` 为 `leanprover/lean4:v4.36.0-rc2`；`lake-manifest.json` 含依赖 URL、解析后的 `rev`、配置文件等，并标记 `fixedToolchain: true`。这是可查版本实例，不是推荐直接部署 RC 或任意“最新版”。[S4、S5]

本次检查的 Lean master 提交 `19c079dffa0c21eb9cdc9d3f709c430c8d882538` 与上述 Mathlib 不构成已验证兼容组合。源码调查使用它来固定事实来源；未来运行应从选定 Mathlib 的工具链要求出发，另验收兼容性。[S2–S5]

`.olean` 是构建/导入产物，官方另提供重放检查，说明保存或加载编译产物不能替代完整信任判断。Mathlib 构建产物复用、应用的目标证明缓存、模型响应缓存是不同对象，不能互相继承“已验证”状态。[S1；后一句为工程区分]

## 2. 建议的可信检查链

1. **先冻结规格。** 可信侧生成只读 challenge，绑定题文身份、ProblemSpec 版本、变量类型、量词、局部假设、定义域及全部义务。候选仅提供证明内容；候选不能自行决定最终目标、导入集或公理政策。[S1、R4]
2. **在隔离环境构建。** 通过现有 Registry、Job 预算及产物权限边界新增专用后端；镜像和依赖在可信准备阶段固化，运行时禁网，不接受客户端任意镜像或项目配置。生成 Lean 的构建与 elaboration 也在隔离范围内。当前 Python 容器内存/CPU 值不能直接视为 Lean 已校准值。[R2；建议]
3. **检查目标与证明。** 等待所有检查完成，核对指定目标真实存在、完整类型/引用定义与 challenge 相符、证明可核验；不依据候选打印的成功文本或单独退出码授予证明状态。对未审阅生成程序，采用官方增强验证链并记录实际检查器；未部署该链时明确较弱信任范围。[S1、S3]
4. **审核公理闭包。** 对实际最终目标计算传递公理，拒绝 `sorryAx` 和所有政策外公理。标准三公理可按数学政策允许，严格子域可更窄；不按名字模式自动放行新增公理。同时审查目标中的局部前提。[S1–S3]
5. **绑定证据再投影等级。** 保存命令、环境、输入目标、证明/源文件、检查器、公理结果、stdout/stderr 与退出和清理状态的内容引用；绑定同一 Run、义务、图版本、规格和产物版本。规格未审阅时仅显示“形式目标通过，原题对应待复核”。[R1、R2、R4；建议]

以上链条是技术可行建议，不是已运行产品证据。若只验证可信、人工审阅的固定证明，可以采用较小检查路径；任意生成程序不得沿用该路径的信任假设。[S1]

## 3. 环境和缓存身份建议

| 固定对象 | 建议记录 | 作用 |
| --- | --- | --- |
| 工具链 | Lean 版本/提交、分发二进制校验值、Lake 版本、`lean-toolchain` 内容 | 避免仅记录浮动别名 |
| 数学环境 | Mathlib 完整提交、全部依赖解析 rev、manifest 和 lakefile 内容、导入模块及其来源 | 防止同名定理或模块掩盖定义改变 |
| 执行与核验 | 镜像 digest、平台/架构、构建选项、检查器版本、合法公理政策及模板版本 | 明确信任和复现条件 |
| 数学身份 | elaborated 目标类型、局部上下文、宇宙/隐式参数和引用定义身份、规范化算法版本 | 避免只用展示字符串判等 |
| 证据与归属 | 源文件/证明引用及 hash、规格版本、义务 ID、用户/工作区/来源 Run | 绑定结论与访问边界 |

这是根据官方版本文件和现有产物合同提出的记录集合，不声称上游提供同名 environment_id 标准。[S4、S5、R2]

首版缓存只做精确身份匹配；相似文本或向量检索只用于推荐候选。缓存项包含目标、假设、声明/依赖、环境、公理和规格政策身份。命中后把证明放入当前可信 challenge 重新检查目标与公理；重新检查通过才能产生当前 Run 的新回执。仅有旧 hash 或历史 PASS 不足以升级当前目标。[S1、R4；建议]

改变定义域、局部前提、定义/导入、依赖提交、检查政策或目标版本时保守失效。暂不实现跨环境证明迁移或语义等价缓存键；避免为了命中率引入无法审计的归一化。用户/工作区归属与数学正确性分别检查，模型看到的历史经验仍不是已证前提。[R2、R4；建议]

## 4. 最小领域及拟验收案例

建议第一片只接可信预置目标：有理数上的多项式恒等式，允许固定变量与四则中的加、减、乘、自然数幂，首版排除除法、根式、超越函数和自动从自然语言抽取任意规格。可先用 `rfl` 或固定 Mathlib tactic 生成证明项，再由上述检查链验证；具体 import/tactic 在选定工具链下另行执行验收。本轮没有运行这些示例。

| 拟用例 | 预期行为 | 区分的边界 |
| --- | --- | --- |
| 可信目标 `(x + y)^2 = x^2 + 2*x*y + y^2`，变量为有理数 | 真实证明和检查完成后只给该目标通过 | 正向最小闭环 |
| 同一固定目标但证明无法完成 | 未证成，保留真实诊断 | 证明失败不等于命题为假 |
| 依赖中含 `sorry`，或目标传递使用政策外公理 | 拒绝证明升级，报告公理审计结果 | 不依赖源码字符串扫描 |
| 原题无条件，形式目标多出未经授权前提 | 即使条件证明通过也不授予原题 L3 | 公理审计不替代规格对应 |
| 原题要求充要条件/完整解集，只核验一个方向或候选 | 仅记录已检查义务，整题不完整 | L2 不冒充 L3 |
| 缓存命中但定义域、目标或依赖版本已变 | 不直接复用旧 PASS，重新检查或失效 | 跨题复用身份 |
| 目标证明通过，原题/ProblemSpec 对应待审阅 | 形式目标通过、原题待复核 | 语义诚实展示 |
| 后端 timeout、取消、编译错误或证据缺失 | 未证成并保存执行原因，不生成反例结论 | 执行和数学状态分层 |

自然语言层需要审阅变量域、量词、必要充分性、存在/唯一性、最优值取得性及图形隐含条件。第一片可通过用户审阅可信规格限制责任范围；不能承诺自动判定任意中文题与 Lean 目标语义等价。[S1、R4；建议]

## 5. 后端结果与能力评价建议

`SOLVED` 仅表示所声明范围内的完整目标、证明和政策检查通过；`PARTIAL` 必须列出已通过与未通过义务，不能隐去不完整部分。`FAILED` 表示本次尝试未证成，`TIMEOUT`/`ERROR` 表示执行没有取得合格证据，均不能写成命题已反驳。反驳另需适用域正确且独立核验的反例或否定命题证明。[R4；建议]

生成能力另设固定题目、模型、模板、预算和环境，记录完整分母、规格通过率、证明生成通过率、检查成本、超时/未知数及端到端原题完成率。先取得预置证明的真实回执，再评估生成，最后评估缓存复用频率和总成本；不以缓存命中率或适配器存在替代数学效果证据。[R3、R4；建议]
